# 스펙 — 수업일지 트레이너 수정·삭제(void) + 이의 해소 루프

> **협업:** 웹Claude 스펙 → 클로드코드 구현 → 대수 커밋. additive 신규 UI + 작은 마이그레이션 1개. 교훈1 하드닝 필수. anon-open 금지.
> **배경:** 수업일지 회원 확인·서명(직전 스펙) 후속. 회원이 '이의'하면 트레이너가 그 일지를 **고치거나 지울** UI가 없고(PtWorkoutTab 타임라인 렌더 전용 · 코드 주석 "voided 무르기·session_at 수정은 후속"), 이의가 들어와도 **회원이 재확인할 길이 없다**(dispute는 pending에서 영구 제외). 이 둘을 채운다.
> **근거(실제 소스):** `components/views/PtWorkoutTab.jsx`(타임라인·voided 표시 有, 편집/삭제 버튼 無) · `docs/migrations/2026-07-08-step7b-partb3-rls-lock.sql`(`auth_all_daily_workout_log` = `for all` account 스코프) · `app/m/[token]/page.jsx`(회원 pending 필터 `confirm_result !== 'dispute'`).

## 0. RLS 현황 (중요 · 확인됨)
- `daily_workout_log`: **`auth_all_daily_workout_log` (`for all` to authenticated · `account_id = auth_account_id()`)** 존재 → 트레이너 **UPDATE·DELETE 이미 허용**. 수정·void에 **새 정책 불필요**. (교훈1 `.select()`만.)
- `workout_log_confirmation`: 현재 트레이너 **SELECT만**. 이의 해소(§3)를 위해 **트레이너가 dispute 행만 손대는 정책 1개** 신규 필요(confirm 행은 절대 불변=증거).

## 1. 수정 — `ai_summary` 인라인 편집
- 타임라인 각 로그 카드에 **[수정]** 버튼 → 인라인 `textarea`로 `ai_summary` 편집 → `update daily_workout_log set ai_summary=... where id=<log.id>` + `.select()`(0행이면 실패 처리·교훈1).
- 편집 범위: **`ai_summary`**(회원이 보고 확인하는 내용). `session_at`(날짜) 편집은 넣어도 좋음(선택). `sets_structured` 편집은 후속(입력 UI 복잡).
- ⚠️ **확정(confirmed)된 로그를 수정하면** 저장 해시와 어긋나 트레이너 화면에 "확인 후 변경됨 ⚠️"이 뜬다(의도된 감사 신호 · 이미 구현). 확정 로그 수정 전엔 "이미 회원이 확인한 일지예요. 수정하면 '변경됨'으로 표시됩니다" 경고 권장.

## 2. 삭제 = void(소프트) 권장
- **[삭제]** 버튼 → 확인 다이얼로그(`Modal`) → `update daily_workout_log set voided=true where id` + `.select()`. `voided`는 **기존 소프트삭제 플래그**:
  - 회원 뷰(`member_workout_log`)에서 숨겨짐(voided 필터 이미 있음).
  - **잔여 차감 되돌림**(잔여 = 계약 − 비voided 로그 count) = 안 한 수업이면 세션이 복구됨.
  - voided 로그는 타임라인에 흐림+취소선+"취소됨"으로 남음(이미 구현) → **[무르기]**(voided=false)로 되돌리기 가능.
- ⚠️ **하드 DELETE는 비권장** — `workout_log_confirmation.log_id`가 `on delete cascade`라 **회원 서명·이의 기록까지 함께 사라진다**. 소프트 void가 감사·되돌리기 우위. (진짜 물리 삭제가 꼭 필요하면 별도 결정.)
- ⚠️ **오운완 집계(`ounwan_stats`/`ounwan_days` RPC)가 voided를 제외하는지 확인** — 안 하면 void해도 출석·연속에 남는다(불일치). 제외 안 하면 RPC에 `and coalesce(voided,false)=false` 추가.

## 3. 이의 해소 루프 (핵심 · §3-A/B 중 택1 필요)
**문제:** 회원 pending 필터가 `confirm_result !== 'dispute'`라, 이의된 로그는 회원 게이트에서 영구 제외 → 트레이너가 고쳐도 **회원이 재확인 못 함**. 트레이너가 이의를 "해소"하면 그 로그가 회원 pending으로 **다시 돌아와 재확인**되게 해야 완결.

- **void한 경우:** 로그가 회원 뷰에서 숨으니 이의는 **자동 moot**(별도 해소 불필요).
- **수정(내용 정정) 경우:** 이의 행을 "해소" 처리 → `confirm_result`가 null이 되어 pending 재진입 → 회원이 정정된 내용을 재확인.

**해소 방식 — 택1:**
- **A) `resolved_at` 플래그 (권장 · 감사 보존):** `workout_log_confirmation`에 `resolved_at timestamptz` 컬럼 추가. 트레이너 "수정 후 재확인 요청" 시 그 로그의 dispute 행에 `resolved_at=now()` UPDATE. **뷰의 `confirm_result` 집계를 `result='dispute' and resolved_at is null`만 dispute로** 치도록 수정 → 해소된 dispute는 `confirm_result=null` → pending 재진입. "회원이 한때 이의했다 → 트레이너가 해소" 이력이 남는다.
- **B) dispute 행 DELETE (경량):** 트레이너가 그 로그의 dispute 행을 삭제 → `confirm_result=null` → pending 재진입. **단 이의 이력이 사라진다**(증거성↓).

→ **추천 A**(증거 시스템이라 "이의했다"는 사실을 지우지 않는 게 맞음). B는 코드 최소.

**신규 RLS(어느 쪽이든):** `workout_log_confirmation`에 트레이너 정책 1개 — A면 UPDATE(resolved_at), B면 DELETE. **반드시 `result='dispute'`에 한정 + account 스코프**. confirm 행은 트레이너가 UPDATE/DELETE 불가(회원 서명 불변).
```sql
-- (A안 예시) 트레이너가 자기 account 회원의 '이의' 행만 해소 표시. confirm 행은 손 못 댐.
drop policy if exists "trainer_resolve_dispute" on workout_log_confirmation;
create policy "trainer_resolve_dispute" on workout_log_confirmation
  for update to authenticated
  using (result = 'dispute' and exists (
    select 1 from daily_workout_log d join user_table u on u.id = d.user_id
    where d.id = workout_log_confirmation.log_id and u.account_id = auth_account_id()))
  with check (result = 'dispute');
-- + alter table workout_log_confirmation add column if not exists resolved_at timestamptz;
-- + 뷰 confirm_result 집계에 'and resolved_at is null'(bool_or(result='dispute' and resolved_at is null))
```

## 4. UI (PtWorkoutTab 타임라인)
- 각 로그 카드에 **액션 행**: `[수정]`(ghost) · `[삭제]`(danger). voided면 `[무르기]`만.
- 이의 상태(Badge "이의제기")인 로그는 **[수정 후 재확인 요청]**(= ai_summary 편집 + 이의 해소(§3))을 눈에 띄게. 이걸 눌러 고치고 저장하면 회원에게 다시 확인 요청이 간다(pending 재진입).
- 삭제·확정로그 수정은 **확인 다이얼로그**(`Modal`). 기존 DS(`Button`·`Modal`·`Field`/`Textarea`) 재사용 — 손수 만들지 말 것.

## 5. 검증 / 교훈1
- 모든 write(update/void/resolve)에 `.select()` → `error||!data||length===0`이면 실패.
- 수정 → 회원앱에서 정정 내용 보임. void → 회원 뷰·잔여·오운완에서 빠짐, 무르기로 복구.
- **이의 해소 후 회원 pending 재진입**(그 로그가 다시 "확인 안 한" 목록에 뜸) → 회원 재확인 → confirm_result 'confirm'(우선).
