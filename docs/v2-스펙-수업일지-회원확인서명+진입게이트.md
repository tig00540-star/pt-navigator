## 0. 무엇을·왜 (불변)

회원이 회원앱에서 자기 **수업일지(운동일지 = `daily_workout_log`, "수업확인서 겸 운동일지")** 를 보고 **확인/이의**하면 종이 수업확인 서명을 대체한다. 로그인 시 미확인분이 있으면 **유도**한다(강도는 §4). `session_log`(계약)는 이번 스코프 아님.

**대전제(불변):** ① 확인/이의 **두 갈래**(확인만 강요 금지 = 자유의사여야 증거력 성립) ② 실패 시 **fail-open**(락아웃 금지) ③ 오늘 수업 **유예** ④ 게이트는 UX 유도, **진실은 확인 레코드** ⑤ 본인확인 현행 유지(토큰+뒤4자리, OTP 후속) ⑥ 탭 확인 기본, 손서명 후속.

## 0.5 이번 MVP 스코프 (리뷰 반영 확정)

| 항목 | 이번 | 후속 |

## 1. 데이터 모델 — 신규 append-only 확인 테이블

`daily_workout_log`에 컬럼을 붙이지 않고 별도 테이블(append-only 감사 레코드 · 회원 쓰기 전례 `cardio_log`와 결 동일).

`docs/migrations/2026-07-21-workout-confirmation.sql`

```sql
create table if not exists workout_log_confirmation (
  id            uuid primary key default gen_random_uuid(),
  log_id        uuid not null references daily_workout_log(id) on delete cascade,
  member_id     uuid not null,                                 -- = user_table.id(확인한 회원)
  result        text not null check (result in ('confirm','dispute')),
  method        text not null default 'tap' check (method in ('tap','drawn')),  -- drawn은 스키마만·구현 후속
  signature_path text,                                         -- drawn 전용(이번엔 항상 null)
  content_hash  text,                                          -- 확인 시점 일지 내용 동결 해시(서버 계산)
  dispute_note  text,                                          -- result='dispute'일 때 사유
  confirmed_at  timestamptz not null default now()             -- ★서버 시각(권위)
);
-- ★수집 안 함: IP·User-Agent 등(증거는 confirmed_at+content_hash+member_id로 성립 · 불필요 저장 회피)
create unique index if not exists workout_log_confirm_once
  on workout_log_confirmation (log_id) where result = 'confirm';   -- 확인 1건/일지(이의는 다건 허용)
create index if not exists workout_log_confirmation_member_idx
  on workout_log_confirmation (member_id);

alter table workout_log_confirmation enable row level security;

-- 회원: 본인 것만 SELECT(상태 표시). 쓰기는 서버 라우트만(§3) → 회원 INSERT/UPDATE/DELETE 정책 없음.
drop policy if exists "member_read_own_confirm" on workout_log_confirmation;
create policy "member_read_own_confirm" on workout_log_confirmation
  for select to authenticated using (member_id = auth_member_id());

-- 트레이너: 자기 account 회원의 확인만 SELECT.
drop policy if exists "trainer_read_account_confirm" on workout_log_confirmation;
create policy "trainer_read_account_confirm" on workout_log_confirmation
  for select to authenticated
  using (exists (
    select 1 from daily_workout_log d
    join user_table u on u.id = d.user_id
    where d.id = workout_log_confirmation.log_id
      and u.account_id = auth_account_id()      -- ⚠️ user_table의 account 스코프 컬럼명 라이브 확인
  ));
```

> **v2.1:** `member_ip`(개인정보·리뷰 ③)와 `member_ua`(위조 쉬움·저장 이유 약함·리뷰 ①)를 **둘 다 제거**. 증거는 `confirmed_at`+`content_hash`+`member_id`(JWT 검증)로 성립 — "이 회원이 이 시각에 이 내용을 확인/이의"가 남는다. 필요해지면 컬럼 추가는 쉽다.

## 2. 뷰 확장 — `member_workout_log`에 확인 상태 append

⚠️ **정정(리뷰 ①):** `create or replace view`는 **출력 컬럼 목록만** 제한한다(같은 컬럼명·순서·타입 유지 + 뒤에 추가 가능). **FROM/JOIN 구조는 완전히 바꿔도 된다**(PG 문서: "계산식은 완전히 달라도 된다"). 따라서 아래처럼 lateral join을 얹어도 create-or-replace로 **통과**하며, **권한(grant)이 보존**된다 — 이게 "drop하면 권한 날아감" 함정을 피하는 정답. 기존 소비처(달력·그래프·수업일지)는 **append-only + left join(limit 1) + 필터 동일**이라 영향 없음.

```sql
create or replace view member_workout_log
  with (security_invoker = false) as
  select d.id, d.created_at, d.ai_summary, d.session_at, d.sets_structured,   -- ★기존 5컬럼 순서·타입 불변
         c.confirmed_at,
         c.result as confirm_result                                           -- 'confirm'|'dispute'|null
  from daily_workout_log d
  left join lateral (
    select confirmed_at, result from workout_log_confirmation
    where log_id = d.id and result = 'confirm' order by confirmed_at limit 1
  ) c on true
  where d.user_id = auth_member_id()
    and coalesce(d.voided, false) = false
    and coalesce(d.source, '') <> 'noshow';
grant select on member_workout_log to authenticated;
revoke select on member_workout_log from anon;
```

**⚠️ 착수 첫 관문(리뷰 ⑥):** 라이브에서 위 `create or replace`를 **먼저 dry-run**한다(뷰 안 바뀌면 게이트 전체가 안 돎). 만에 하나 실패하면 **`drop view` → `create view` → `grant select … to authenticated` → `revoke select … from anon`** 4문 세트로. dry-run 검증: `select pg_get_viewdef('member_workout_log'::regclass, true);` 로 5컬럼+2추가·필터 확인.

## 3. 확인 쓰기 경로 — 서버 라우트 `app/api/member-confirm/route.js`

서버 라우트로(직접 클라 insert 아님) — 증거력의 **무결성·본인확인**을 클라에 안 맡긴다. `/api/member-auth`와 같은 결.

```
POST /api/member-confirm  { log_id, result, dispute_note? }   // method는 이번엔 서버가 'tap' 고정
1. Authorization: Bearer <회원 access_token> 검증 → member_id. 없으면 401.
2. service_role로 daily_workout_log 조회: id=log_id AND user_id=member_id.
   없으면 403 · voided/noshow면 400(확인 대상 아님).
3. result='confirm'인데 이미 confirm 존재(unique 위반) → 409.
4. content_hash = sha256(`${ai_summary}|${session_at}|${sets_structured ?? ''}`).  // ★confirm·dispute 둘 다 계산 = 그 시점 내용 동결(이의도 "이 내용 보고 이의"의 증거)
5. insert workout_log_confirmation(...) .select();  // 교훈1: 0행이면 실패(500). ★IP·UA 등 미수집
6. return { ok:true, confirmed_at }.
```
- 키 부재/DEMO(service_role 없음): 503 → 클라는 게이트를 **끈다**(fail-open, §4).
- **손서명은 이번 미구현**(리뷰 ⑤). `method`는 서버가 `'tap'` 고정, `signature_path` null. 후속에 drawn 분기 추가.

## 4. 회원앱 진입 유도 (`app/m/[token]/page.jsx` · MemberHome)

**기본 = 소프트 유도(리뷰 ④ · 하드 blocking은 이탈+증거력 약화).** 주입: `loadHome()` 후 `phase==="home"`, `logs`(=member_workout_log, `confirmed_at` 이미 실림) 기반.

미확인 대상:
```js
const KST_today = todayStr();
const pending = logs.filter(l =>
  !l.confirmed_at && l.confirm_result !== 'dispute' &&
  l.session_at && l.session_at < KST_today            // 유예: 오늘만 제외(확정)
);
```

동작(단계적 강도):
1. **항상: 홈 상단 배너 + 각 일지 카드에 '미확인' 뱃지.** 배너 = "확인 안 한 수업일지 N건 · 확인하기" → 누르면 확인 시트. **회원은 앱을 그대로 쓴다**(오운완·기록 열람 안 막음).
2. **`pending.length >= THRESHOLD`(기본 3, 상수)**: 로그인 직후 **소프트 blocking** 모달(`Modal`, 단 **`blocking`이 아니라 닫기 가능**) — 큐로 한 건씩 확인/이의 유도하되, **[나중에 할게요]** 버튼으로 빠져나갈 수 있다(하루 1회까지; 그 이상은 배너로만). 이게 "자유의사" 보존 + 이탈 방지.
3. 각 확인 카드: `session_at` + `ai_summary`(+sets 요약). **[확인]** → `POST /api/member-confirm {result:'confirm'}`. **[이 수업 안 받았어요]** → 사유(선택) → `{result:'dispute', dispute_note}`. 성공 시 큐에서 제거·다음.
- ⚠️ **fail-open:** `logs` 로드 실패(기존 catch) 또는 `member-confirm` 503(데모)면 **유도/게이트 전부 끔.** 회원 절대 락아웃 금지.
- ⚠️ **이의 출구 상시 활성**(자유의사).
- 컴포넌트 신설 `ConfirmFlow`({logs, onDone}) — 배너·뱃지·확인시트. **기존 DS(`Modal`·`Card`·`Button`·`Badge`) 재사용.**

> **하드 blocking을 원하면(대수 옵션):** 위 2단계를 `Modal blocking`(닫기·ESC·배경 무시)로 바꾸고 THRESHOLD=1. 단 "나중에" 탈출구는 남길 것(순수 강제는 증거력 약화). **추천은 소프트.**

## 5. 트레이너 화면 표시 (additive)

수업일지 목록/PT뷰 각 일지에 **회원 확인 상태 뱃지**(`workout_log_confirmation` 트레이너 SELECT 정책 조회):
- `확인됨 ✓ (날짜)` (`Badge` primary/neutral) · `미확인` · `이의제기`(`Badge` danger).
- **★해시 대조(리뷰 ②):** 확인된 일지는 **현재 `ai_summary/session_at/sets_structured`로 해시를 재계산**해 저장된 `content_hash`와 비교 → 불일치면 **"확인 후 내용 변경됨 ⚠️"** 뱃지. 이게 있어야 저장한 해시가 실제 증거가 된다(대조 안 하면 죽은 데이터). 저장·대조 로직은 이번, 표시는 이번 또는 바로 후속이되 **설계 의도는 지금 명시**.
- 이의 건은 눈에 띄게(후속: 알림/할일 연동).

## 6. (후속) 손서명 — 이번 미구현
`method='drawn'` 분기 · 비공개 버킷 `member-signatures`(경로 prefix `member_id/` RLS) · canvas→PNG 여백트림·압축 → 업로드 → `signature_path` 전달. **이번 스코프 제외**(리뷰 ⑤). `method` 컬럼만 미리 있음.

## 7. 착수 순서 (리뷰 ⑥ 반영)
1. **뷰 dry-run 먼저** — §2 create-or-replace가 라이브에서 통과하는지(안 되면 4문 세트). **첫 관문.**
2. 마이그레이션 테이블+RLS → 실행 → 기록본.
3. 뷰 확장 실제 적용 → 회원앱 `logs`에 `confirmed_at` 실리는지(게이트 없이).
4. `/api/member-confirm` → curl로 확인/이의/스코프/재확인(409)/데모(503) 검증.
5. `ConfirmFlow`(배너+뱃지+소프트 유도) + MemberHome 주입(fail-open).
6. 트레이너 뱃지 + **해시 대조 표시**.

## 8. 검증
- 회원 세션 `GET member_workout_log` → `confirmed_at`·`confirm_result` 실림, 기존 컬럼·달력·그래프 불변.
- 미확인 2건 회원 로그인 → **배너+뱃지 뜨고 앱은 정상 사용**. 확인 → 재조회 시 `confirmed_at` 채워지고 배너 감소.
- pending ≥ THRESHOLD → 소프트 모달 뜸 + [나중에] 로 빠져나가짐.
- 이의 → dispute 레코드·트레이너 '이의제기' 표시.
- 확인 후 트레이너가 `ai_summary` 수정 → 트레이너 화면 "변경됨 ⚠️".
- fail-open: 네트워크 끊고 로그인 → 유도 없이 home.
- 재확인 409 · 남의 log 403 · 회원 직접 insert 시도 0행(정책 없음).
- lint·prod build green.
